## Scope and status

This is an architecture threat model for THIS_REPOSITORY, Scientist-One vNext. It is source-backed and repository-wide, but it is not a vulnerability audit and does not turn abuse hypotheses into findings. The inspected system is a local-first Python research controller with captured-source startup, typed orchestration and scientific state, a content-addressed artifact registry, an append-only event ledger, controlled external adapters, a credential-bearing live-egress kill switch, a run-bound credentialless HMAC gateway authority, prospective Dataset/Split custody, Result-v2/StatisticalTest completion authority, canonical ClaimSemantics and claim-bound semantic review, source-owned Ablation authority, a closed-catalog autonomous implementation boundary, local and provider-neutral experiment backends, scientific gates, and an artifact-derived paper boundary.

The bundled Research OS path is a synthetic integration fixture. Its top-level `PASS` means system-fixture integrity only. It does not establish publishable science, novelty, live external validation, independent custody, scientific-result-eligible local execution, or human E4 release authority (`src/scientist_one/research_os.py`, `_execute_research_os_fixture()`, `_run_research_os_fixture()`, and `run_research_os_fixture()`).

This snapshot intentionally contains no final test count, audit count, or frozen source digest. Those belong to the final captured evidence run after the tree is frozen. The project audit must be the last repository mutation; its own machine authority will be `reports/final_audit.json`, not a digest backfilled into this document afterward.

## Architecture and materially different startup paths

### Supported production path

```text
/opt/homebrew/bin/python3 with -I -S -B
  -> scripts/scientist_one_cli.py captures and attests package bytes
  -> scientist_one.cli requires the isolated-launcher marker
  -> ScientistOneOrchestrator admits and pins the project-root identity
  -> @_project_command holds the root/resource guard
  -> research_os_fixture()
  -> run_research_os_fixture(canonical admitted root)
```

The launcher rejects missing isolation flags, opens and bounds package source without following links, executes captured source through an exclusive loader, requires the canonical current directory, attests the live tree, and sets the final production marker immediately before CLI dispatch (`scripts/scientist_one_cli.py`, `_verify_startup()`, `_CapturedTree`, `_CapturedSourceLoader`, `_attest_loaded_modules()`, and `main()`). The CLI's module-level captured-import admission refuses an ordinary direct import, and `main()` separately requires the isolated-launcher marker (`src/scientist_one/cli.py`). The orchestrator pins the admitted root and serializes public commands under its root guard (`src/scientist_one/orchestrator.py`, `ScientistOneOrchestrator.__init__()`, `_project_command()`, and `ScientistOneOrchestrator._command_root_guard()`); `ScientistOneOrchestrator.research_os_fixture()` is decorated with that guard.

### Direct integration-test path

```text
captured unittest environment
  -> direct import of run_research_os_fixture
  -> temporary canonical root
  -> fixture execution without CLI/orchestrator command admission
```

`run_research_os_fixture()` deliberately retains direct calls for isolated integration tests while documenting the supported CLI's admitted-root capability (`src/scientist_one/research_os.py`). The semantic-adversarial Research OS E2E invokes that direct API in copied temporary roots (`tests/test_research_os_e2e.py`, `test_real_local_fixture_materializes_conservative_authorities`). Separate operations coverage invokes the decorated orchestrator method and therefore traverses `_project_command`, but constructs the orchestrator under mocked captured-root admission rather than the captured launcher (`tests/test_vnext_operations.py`, `test_guarded_launch_capability_is_production_bound_and_one_shot` and `test_complete_fixture_rehydrates_all_authorities_and_count_tampering_fails`). The CLI dispatch test substitutes a mocked orchestrator (`tests/test_vnext_cli.py`, `test_fixture_dispatch_uses_guarded_orchestrator_and_canonical_json`). These tests compose useful coverage, but no single current E2E traverses captured production startup, CLI dispatch, guarded orchestration, child execution, and completed authority rehydration together.

### Scientific data flow

```text
confined fixture / controlled external bytes
  -> typed normalization and deterministic checks
  -> prospective Dataset/license/use and exhaustive Split authority
  -> immutable registry objects with parent closure
  -> run-scoped ledger checkpoint
  -> current Result/optional StatisticalTest bundle completion
  -> canonical research state and source-owned claim/evidence receipts
  -> E -> G -> P -> Jref -> K citation/semantics authority
  -> scientific gates
  -> artifact-derived paper verification
  -> human-review candidate only (E4 unavailable)
```

Each integrated phase verifies registered artifacts before recording its ledger checkpoint and labels the ordering `REGISTERED_BEFORE_CONSUMPTION` (`src/scientist_one/research_os.py`, `_phase_checkpoint()`). Canonical state similarly validates current registry and ledger state, checks authority and parent freshness, registers canonical bytes, and then appends a materialization event (`src/scientist_one/research_state.py`, `ResearchStateRepository.materialize()` and `ResearchStateRepository.validate_state()`). Registry and ledger writes are individually locked and durable, but they are not one cross-file transaction.

## Assets

1. **Scientific identity:** exact code, data, configuration, evaluator, protocol, method, seed, ablation, environment, and backend identities.
2. **Scientific result integrity:** recomputable per-subject correctness, seed completeness, baseline equivalence, ablation semantics, statistical controls, and domain-validity results.
3. **Provenance and ordering:** registry bytes/metadata/parent closure, ledger history, canonical-state lineage, checkpoints, and evaluator decisions.
4. **Run uniqueness and recovery state:** the atomic run reservation and bounded operation receipt, including preservation of failed/partial identifiers.
5. **Claim authority:** claim text, typed evidence-use class, evidence links, content-bound support receipts, independent verifier identity, and live writer view.
6. **Paper truthfulness:** exact authoritative metrics, units, directions, method/code bindings, reference depth, assets, limitations, hard blockers, and release label.
7. **Custody and confidentiality:** unrevealed holdout bytes and their one-shot journal within the explicitly non-independent local model.
8. **Credentials and external provenance:** provider secret values in process memory, the rule that unverified transports receive no resolved credential, the credential-bearing live-dispatch prohibition, the local gateway-authority HMAC key, credentialless redacted request intent and raw response bytes, licensing/retention status, retry budget, and terminal external outcome.
9. **Autonomous implementation authority:** the closed reviewed catalog, exact worker code/configuration, declared parent evidence, admission/descriptor/run-spec receipts, and the boundary between provider selection and executable authority.
10. **Execution-plan custody:** canonical adaptive-plan bytes and their exact per-run job/backend/frozen-spec submission/collection binding.
11. **Terminal scientific truth:** typed terminal derivation, evidence parents, raw terminal bytes, canonical decision, ledger event, and final-summary reference.
12. **Resource and validity budgets:** elapsed time, disk/memory/thermal observations, concurrency, crash/stall state, exploratory usage, and protected confirmatory reserve.
13. **Human authority:** the distinction between same-process logical review, human gates, independent external validation, and unavailable human-only E4.
14. **Dataset and split truth:** prospective source/body/license/use identity, signed credentialless crossing, semantic use judgment, raw manifest, exact experiment projection, exhaustive disjoint partition and pre-result ordering.
15. **Result visibility:** the exact canonical graph, source-owned promotion, current Result/optional StatisticalTest bundle completion and every materialization event.
16. **Writer-visible semantics:** the one coarse ClaimSemantics proposal slot, claim-bound reference and qualifier judgments, exact claim fields/dependencies, outcome ambiguity and retained custody closure.
17. **Ablation and robustness truth:** required intervention/component identity, checked raw output and current state closure, plus the categorical ineligibility of synthetic reproduction.

## Threat actors and attacker capabilities

- **Faulty or malicious local operator:** can choose CLI inputs, run IDs, and project-local files, but should not be able to escape the root, reuse an existing run identity, mint evaluator/E4 authority, or make external content executable.
- **Malicious same-user process:** can race names, replace writable source or evidence, create links, truncate writes, inspect local secrets/holdout files including the gateway HMAC key, and—if it controls the whole workspace and trusted source—coherently recompute ordinary hashes or re-sign rewritten gateway claims. Partial/torn/stale attacks and ordinary caller-forged signed-authority artifacts are in scope; coherent replacement with key/source compromise is an explicit `BLOCKED_LOCAL` limitation.
- **Tampered or malicious experiment program:** can emit structurally valid, hash-consistent false outputs and can attempt host filesystem, process, or network access using the worker's OS permissions.
- **Hostile external service or content author:** can return redirects, oversized/malformed/ambiguous JSON, prompt-like instructions, false citations, misleading metadata, malicious prose, retry pressure, or raw/transformed secret-reflecting bytes. The current gateway prevents such a service from receiving a configured credential through its real-network path.
- **Compromised provider credential/account:** could authorize cost-bearing outbound requests or expose account data if credential-bearing live access were reopened. The current gateway does not dispatch that path; credentials must never become artifacts, log content, or inputs to unverified transports.
- **Developer/test author or accidental API caller:** can introduce a new direct call path, omit an evidence-use classification, weaken a scientific gate, confuse system reproducibility with scientific reproducibility, or cite a direct test API as production admission coverage.
- **Compromised interpreter/host/privileged process:** can subvert the launcher, stdlib, TLS, filesystem, telemetry, and in-process role separation. This actor is outside the promised local defense boundary.
- **Remote unauthenticated attacker:** has no inbound listener in the current architecture. Remote influence is through allowlisted outbound responses, not an exposed server.

## Security and scientific objectives

- Production commands execute only captured and re-attested project bytes under the admitted project-root identity.
- All repository data reads/writes remain confined, bounded, type-checked, and resistant to traversal, symlink, protected-hardlink, special-file, and ambiguous-JSON substitution.
- Network content remains untrusted evidence, never control instructions; all socket ownership remains in the audited gateway.
- A credentialless live crossing is authoritative only when the exact built-in transport consumes the exact one-shot request capability and the resulting HMAC claim is registry- and ledger-resolved. This authenticates the local gateway event, not the remote content's scientific truth.
- Credential values remain gateway/transport-owned, are not persisted, and are never disclosed in documentation or provenance. A resolved credential is never passed to an unverified transport, including a self-reported offline fixture; the only transport eligible to receive one is the exact audited implementation, whose credential-bearing live path is blocked before dispatch. Common reversible-form detection at ordinary custody sinks is defense in depth rather than a claim of arbitrary-transform safety.
- Every authoritative scientific object is content-resolved, parent-closed, registered, ledger-bound, and revalidated before downstream consumption.
- Literature investigation, novelty clearance, checked discovery, superiority promotion, soundness, claim eligibility, and paper readiness consume registry-resolved authorities rather than caller-selected booleans or prose. Synthetic literature still cannot establish real-world novelty.
- Scientific Dataset/Split, Result/StatisticalTest, qualifier and Ablation objects consume exact source-owned authorities and current completion/materialization events. An object type, SHA-shaped field, stale completion, partial publication, or favorable duplicate branch is inert.
- Hash-valid producer output is not treated as semantically valid: seed metrics and ablations are independently recomputed from frozen inputs and evaluator semantics (`src/scientist_one/research_os.py`, `_promote_collected_run()` and `_run_analysis()`; `tests/test_research_os_e2e.py`, `test_hash_consistent_wrong_manifest_metric_fails_semantic_recomputation` and `test_hash_consistent_fabricated_ablation_without_vector_fails_closed`).
- A coding provider never gains free-form executable authority: it may select only a reviewed template and bounded parameters; exact provider-attempt, catalog/review, context/evidence, code/configuration/descriptor/spec, plan/binding, manifest/output, receipt, semantic, ledger, state, and claim/paper-exclusion authorities are revalidated before and after a frozen exploratory `NON_EVIDENTIARY` run. The completed verifier independently recomputes the result rather than trusting a PASS label.
- Every promoted local run binds the exact backend plan bytes to the exact run/job/backend/frozen spec and to agreeing submission/collection identities; a substituted or post-collection plan fails before registry promotion.
- Integrated system-fixture execution remains `NON_EVIDENTIARY` while OS isolation is unavailable; a system reproduction `PASS` cannot become a scientific-result or paper claim (`src/scientist_one/research_os.py`, `_run_experiments()` and `_materialize_core_state()`; `.run/DECISIONS.md`, D-014). The generic backend also fails closed: even a caller-selected `SCIENTIFIC_RESULT_ELIGIBLE` spec needs a successful bound manifest and a non-null backend-private OS-isolation attestation, which no current execution path creates (`src/scientist_one/experiments.py`, `CollectedRun.__post_init__()`, `LocalMacBackend._job_is_scientific_evidence()`, and `LocalMacBackend.collect()`; `tests/test_discovery_experiments.py`, `test_local_backend_scrubs_environment_bounds_logs_and_collects_manifest`).
- Claim graph completeness is independent from scientific use. `ClaimEvidenceUse.{SCIENTIFIC,SYSTEM_FIXTURE,NON_EVIDENTIARY}` classifies use; `EvidenceSupportReceipt` schema 1.1 binds the class to claim/evidence content; the default writer view includes only scientific claims (`src/scientist_one/claims.py`, `ClaimEvidenceUse`, `MaterialClaim`, `EvidenceSupportReceipt`, `ClaimEvidenceGraph.verify_claim()`, and `ClaimEvidenceGraph.writer_view()`).
- Both vNext and legacy synthetic claims are explicitly `SYSTEM_FIXTURE`, and vNext readback proves they are eligible only in an explicit diagnostic view, not the default writer view (`src/scientist_one/research_os.py`, `_build_claim_graph()`; `src/scientist_one/orchestrator.py`, `ScientistOneOrchestrator._handler_claims()`; `tests/test_research_os_e2e.py`, `test_real_local_fixture_materializes_conservative_authorities`).
- Scientific citation support is acyclic and claim bound: inert citation evidence precedes the graph/proposal, the exact audited `Jref` reviews that frozen projection, and final ClaimSemantics replay occurs only afterward. Scope/limitation assertions require separate exact `Jqual` authority over the current Result/Run/bundle completion.
- Legacy and vNext synthetic reproduction packages are always scientifically ineligible. A matching architecture/system replay cannot satisfy scientific `ROBUSTNESS` or repair an ineligible Result.
- Paper readiness consumes artifact-derived controls, exact eligible claims, metrics, units, directions, method/code bindings, limitations, and hard blockers rather than caller-chosen booleans (`src/scientist_one/research_os.py`, `_run_paper_pipeline()`; `src/scientist_one/paper_pipeline.py`, `build_authoritative_research_bundle()` and `verify_paper()`).
- Soundness consumes all 15 exact dimension receipts and all 14 exact Challenger-category reviews. Completeness cannot launder `UNTESTED` work or unresolved findings into a pass.
- Negative, null, invalid, inconclusive, blocked-external, and failed outcomes remain visible. Scientific terminal state uses the exact 11-value Research OS vocabulary; operation `PASS` and `SUCCESS` cannot be silently converted into terminal scientific success.
- Human and scientific gates remain independent, and autonomous code cannot construct or imply human-only E4.

## Assumptions and residual risks

- SHA-256 is assumed collision resistant. Ordinary local digests and hash chains are integrity structures, not signatures, secure timestamps, or independent witnesses. The credentialless live-gateway execution receipt adds a narrow HMAC authentication tag, but its key/verifier remain local and it is still not an independent witness.
- The selected Python interpreter, standard library, operating system, filesystem primitives, TLS trust store, and current host are trusted. The launcher does not defend against their compromise.
- Same-user coherent rewrite is not prevented. The system meaningfully detects namespace races, torn writes, stale parents, corrupt hashes, missing receipts, inconsistent histories, and ordinary caller-forged HMAC artifacts; it cannot authenticate a fully rewritten local universe when the attacker also controls the HMAC key or trusted signer/verifier source.
- `LOCAL_MAC` lacks an OS-enforced experiment sandbox. This is `BLOCKED_LOCAL`, not a documentation-only limitation (`.run/ISSUES.md`, `EXT-007`). Integrated and generic current paths both remain non-evidentiary because no backend-verified isolation attestation exists.
- `SimulatedHoldoutCustody` is a durable local one-shot adapter, not independent secrecy or institutional custody.
- Live OpenAI, scholarly, GPU-cloud, licensing, account/cost, independent reproduction, external validation, and E4 paths remain `UNTESTED`, `BLOCKED_EXTERNAL`, or boundary-only as recorded in `.run/ISSUES.md`, `EXT-001` through `EXT-008`. Credential-bearing response custody is additionally `BLOCKED_LOCAL`.
- The source-owned Dataset/Split, Result/StatisticalTest, ClaimSemantics/`Jref`/`Jqual`, and v2 Ablation paths prevent local substitution but cannot clear missing live acquisition, OS isolation, independent semantic review, confirmation or external reproduction. Synthetic reproduction is always scientifically ineligible.
- No inbound web server or remote authenticated API exists. Browser CSRF/XSS and multi-tenant authorization are outside current scope; outbound response handling and credential protection are in scope.
- Direct integration APIs are trusted test surfaces. If any become externally reachable or supported production APIs, they require the same root/source/authorization admission as the CLI.
- The autonomous implementation fixture's scientific/adversarial reviewer roles are in-process logical roles, not independent review or E4; catalog review artifacts authorize only the exact closed worker bytes and bounded component fixture.
- An operation receipt is an operational recovery aid. It is outside the scientific registry and must never be accepted by itself as completed system-fixture authority, scientific evidence, evaluator authority, or paper readiness. Completed status/verify independently rehydrate all named authorities.
- Registry-first/ledger-second ordering makes materialization resumable and verifiable but not transactionally atomic. Orphaned registry objects are a recoverability concern and carry no authority without the corresponding ledger binding.
